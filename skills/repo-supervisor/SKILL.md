# Repo Supervisor

Guide repository work end to end, sizing independent work to available model capabilities, preserving resumable per-repository history, and delivering verified task units while protecting unrelated user changes.

## Workflow

1. **Resume and establish the actual state.** At the repository root, read `.repo-history/meta.json` when present, then open the indexed active or latest relevant task entry. Verify its branch, commit, changed files, and claims against the live workspace; history is continuity context, not authority over newer user instructions. Read repository guidance such as `AGENTS.md`, then inspect `git status --short --branch`, recent `git log`, and relevant diffs. Treat existing changes as user-owned until their scope is understood. Before implementation, check available active sessions, worktrees, and task claims for the same objective or overlapping write scope. Resume or coordinate existing work instead of starting a duplicate; if ownership cannot be established, investigate read-only. For checkpoints, interruption, and evidence states, read [continuity and evidence](references/continuity-and-evidence.md). Create missing history only when implementation is authorized; a plan-only request remains read-only.
2. **Triage evidence.** Separate concrete unfinished work from historical follow-ups, suggestions, and already-completed items. For a dirty tree, summarize changed areas and risks before proposing next steps. Preserve unrelated staged, unstaged, and untracked work.
3. **Agree on the requested phase.** If the user asks for a plan, explore first, resolve material uncertainties, and provide an implementation-ready plan without changing files. If the user asks to implement, continue through verification and delivery. Do not treat a plan request as implementation authorization. Restate the outcome and invariant internally before acting; ask only about material ambiguity that inspection or a safe experiment cannot resolve.
4. **Size work to capability and separate roles.** Before delegation or a multi-step implementation, read [the execution protocol](references/execution-protocol.md). Choose configurable capability profiles from available models and tools rather than fixed model names or assumed prices. Use stronger reasoning for design, decomposition, uncertainty, and integration review; give bounded executors one objective with minimal context and explicit contracts. Separate designer, implementer, and independent reviewer when the risk warrants it; a reviewer must not merely repeat the implementer's claims. Use a dependency graph and one writer per overlapping scope. Run independent units in parallel only when delegation is available and authorized; otherwise follow the same packets sequentially. Keep simple changes direct.
5. **Implement and measure.** For repeated mistakes, missing behavioral harnesses, or evidence preparation, read [structural learning and project verification](references/verification.md). Prefer domain structure and enforceable checks over repeated instructions; independently challenge test expectations as well as code. Work only within the agreed scope. Read task-relevant repository references and apply relevant domain skills or connected apps when available. Before implementation, turn acceptance criteria into observable outcomes: identify the state, screen, response, or measurement that proves each criterion and capture a baseline when one is available. After integrating a task unit, run its relevant tests and build; for iOS UI or runtime changes, also exercise the real flow on a booted simulator or device and inspect the resulting screen and state. Use equivalent end-to-end runtime checks for other platforms. Compare measured outcomes against the criteria, including relevant success, cancel/failure, and boundary paths. Distinguish unit/build success from product acceptance and compare candidate and baseline failures using the same check and environment where feasible, recording both revisions. If evidence misses a criterion, make the needed scoped fix and repeat the affected measurement and regression checks before delivery. Compilation and source inspection alone do not establish runtime behavior. Record concrete observations and values, the environment used, and any cases that could not be measured; do not describe an unmeasured outcome as verified.
6. **Set up missing task tooling.** If a required build, test, validator, or inspection tool cannot run because an interpreter, SDK, or package is missing, diagnose the specific missing prerequisite and prepare the smallest suitable task-local environment without waiting for the user. Prefer the repository's existing version manager, manifest, lockfile, or documented setup. Otherwise use an isolated virtual environment or temporary tool directory and install only the needed dependency from its trusted source. Rerun the exact blocked check, then continue the workflow. Record portable setup instructions and dependency versions when they matter for resuming; keep machine-specific paths and sensitive logs outside versioned history. Do not silently change global packages, system SDK selection, repository dependency manifests, or use privileged commands just to satisfy a check. Ask only when setup requires credentials, substantial cost, a system-wide/privileged change, or an untrusted source; otherwise set it up and proceed.
7. **Commit and push verified units.** When the user invokes this supervisor workflow to implement repository work, treat task-sized commit and push after successful required checks as standing authorization. Keep each atomic task unit in its own commit; stage only files belonging to that unit and push to the task branch. Do not commit or push unrelated user changes. If a required test or runtime check fails or cannot be performed, fix it or stop before publishing that unit and report the evidence and blocker. Do not force-push.
8. **Handle PRs and merges.** Use a PR for task branches when the repository supports that flow; attach every PR created when artifact attachment is available. Before merging, inspect PR state, head revision, checks, reviews, and branch protection when available. The user’s implementation invocation includes standing authorization to merge the scoped verified task without asking again when required checks pass, there are no blocking review requests or unresolved required threads, the diff is limited to the agreed work, conflicts are resolved, and the target branch is the intended repository branch. Prefer squash for a single task-unit PR unless repo convention indicates otherwise. Never bypass branch protection, required human approval, or failed/pending checks. If a required gate blocks the merge, stop at that gate and report it. After merge, verify the remote result, fetch, fast-forward local `main` only when clean, and confirm final status.
9. **Persist task history.** Keep a small, versioned `.repo-history/` directory at the repository root so another account or session can resume. Use `meta.json` as the index and one Markdown file per task under `tasks/`. The metadata should list stable task IDs, title, status, entry file, last update, branch/commit/PR when known, and file-level next entry points. Each task note should record a concise objective, verified baseline, summary of changes/findings, validation evidence, and exact next files/actions. Checkpoint before handoff, context exhaustion, or an interruption and after meaningful verified units; update the note and index at completion; keep the active task easy to find. Do not store credentials, tokens, private user data, or speculative claims. Keep history focused and append new task entries instead of rewriting unrelated history.

## Documentation alignment and design audit

When asked to audit or improve development documentation, first establish the live implementation and the documented contract separately. Inventory the relevant docs from their indexes, then compare claims against current source, tests, configuration, and dated runtime evidence. Treat plans as intent, current-state documents as summaries, and dated evidence as proof only for the revision it records.

For each material discrepancy, record the competing claim, current evidence, and the decision:

- If current behavior is intentional and consistent with repository constraints, update the documentation to describe the measured behavior and distinguish it from future intent.
- If implementation conflicts with an explicit invariant, approved contract, or demonstrated user need, correct the implementation and its tests, then align the docs to the corrected behavior.
- If evidence does not establish the intended direction, do not silently invent policy. Preserve safe existing behavior, document the uncertainty and options, and ask only for the decision that cannot be grounded in repository evidence.

Also look for documentation design problems: unclear source of truth, missing entry points, duplicated rules that drift, unlinked or unreachable guidance, stale examples, and claims that omit important limits. Fix those within the requested scope, update the owning index, and retain dated evidence as history rather than presenting it as current behavior. Validate document metadata, links, and structure with the repository validator; when implementation changes, use the relevant tests/build and measure affected runtime behavior. Record findings, decisions, edits, validation, and file-level resume points in `.repo-history`.

## Guardrails

- The user’s explicit invocation of this skill for implementation is standing authorization to commit, push, and, when repository merge criteria are met, merge the scoped verified task without seeking another confirmation. A plan-only or read-only review request does not grant this authorization. Clarify unclear scope, target branch, or execution permission before acting. The user’s stop instructions and approval limits take precedence; skill files themselves do not grant permission or override mandatory platform approvals or repository protection. Never bypass required repository gates or merge unrelated work.
- Do not overwrite, discard, reset, or bundle unrelated working-tree changes. If scope ownership is unclear, continue read-only investigation and ask a focused question before touching the ambiguous changes.
- Preserve source provenance, raw evidence, and user saves or fixtures. Use isolated test data and synthetic public examples; do not replace user state to make a test pass. Keep credentials, personal identifiers, local paths, private domains, and project-specific material out of tracked history, examples, and diffs. Inspect the new diff and tracked files before publishing; report suspected existing exposure without echoing values or rewriting history.
- Prioritize the current acceptance criteria. Record optional improvements separately; do not expand scope merely to keep an agent busy or repair unrelated baseline failures.
- Do not call work unfinished solely because a historical document lists it as a follow-up. Check whether it is in the current request and whether its completion criteria still apply.
- If multiple agents work in parallel, reconcile their reports and inspect every changed file yourself before integration. Re-run the consolidated tests and simulator checks on the exact commit candidate; sub-agent checks do not replace final integration verification.
- Keep `.repo-history/meta.json` and task notes self-contained enough to resume after a session or account change, but re-check repository state and active instructions before acting on them.
- Prefer repository-native validation guidance. Do not claim a visual or runtime check from a successful build alone. Record device/runtime, test result, skipped checks, and tool limitations in the PR or final report.
- Treat measured product behavior as the completion gate: compare runtime observations with explicit acceptance criteria and continue fixing scoped gaps until they match. If a required runtime path cannot be measured, report the blocker and stop before publishing that task unit.
- For iOS simulator work, use the Build iOS Apps/XcodeBuildMCP workflow when available. If simulator discovery fails with `simctl` not found, check `xcode-select -p` and `xcrun --find simctl`. A shell command prefixed with `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` is a session-local workaround when it works; XcodeBuildMCP may require the active developer directory to point at the full Xcode installation. Changing that system-wide selection requires administrator authorization; never assume the user's password or silently alter it.
- Use GitHub-connected tools for PRs when available and appropriate. Attach every PR created to the current task when the host provides artifact attachment. Do not report a PR as merged until the merge result and `main` revision confirm it.

## Completion report

State the concrete changes, verification performed and its result, any remaining limitations, the branch/commit/PR/merge when relevant, and whether the working tree and local `main` are synchronized. Update `.repo-history` with the same concise status and next entry points. Keep unrelated historical follow-ups separate from the delivered change.
